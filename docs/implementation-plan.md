# phpbox Desktop 代码实现阶段执行计划

## 1. 目标

本计划为当前仓库的代码实现阶段提供统一执行框架，覆盖以下四类工作：

1. UI 组件 / 页面还原实施
2. CLI 与 Go binding 对接
3. bug 修复与根因追踪
4. 任务验证和回归检查

本计划以以下优先级为准：

1. bash / CLI 真实事实
2. 文件系统真实结构
3. 设计稿与交互基准
4. 代码实现的可维护性
5. 创造性“更优雅”方案

若发生冲突，必须以更高优先级为准。

---

## 2. 基本原则

- 事实优先：任何改动必须先验证 CLI、文件格式、目录结构和命名规则。
- GUI 不是事实源：真实状态变更必须走 CLI 事务流，不允许在前端创造 GUI-only 平行状态。
- 最小修复：只修复当前任务所需范围，不做无关重构。
- 真实验证：每个任务都必须给出最小有效验证命令和结果。
- 设计稿对照：UI 采用原型与实现方案为准，不做“主观优化”。

---

## 3. 工作边界

### 3.1 前端边界

重点目录：
- frontend/src/
- frontend/src/components/
- frontend/src/api/
- frontend/src/stores/
- frontend/src/modules/

要求：
- 与 docs/ui-preview/index.html（最终 UI 交互效果）对照。
- 与 docs/frontend-implementation-spec.md（前端落地实施方案）逐条核对。
- 保持 token、布局、交互和文案一致。
- 不引入新依赖。

### 3.2 Go / binding / engine 边界

重点目录：
- main.go
- tray.go
- internal/bindings/
- internal/engine/
- cmd/

要求：
- 只做真实事实驱动的接口对接。
- 保持绑定层薄，业务逻辑放在真实 CLI / engine 侧。
- 不在 GUI 层制造真实状态。

### 3.3 bug 修复边界

要求：
- 先复现，再定位根因，再修复。
- 不在没有证据的情况下猜测和重构。
- 修复范围必须与 cause 对齐。

---

## 4. 执行路线

### Phase A：事实核实与范围确认

#### 目标
明确真实输入和输出边界，避免错误实现。

#### 执行步骤
1. 阅读项目总纲与工程事实：
   - AGENTS.md
   - README.md
   - 关键目录结构
2. 核实 CLI 真实契约：
   - 命令签名
   - 参数结构
   - 命名规则
   - 文件格式
   - 目录布局
3. 识别当前任务影响面：
   - 前端页面/组件
   - Go binding / engine
   - 文件接口
   - 任务数据流
4. 确认最小验证命令：
   - UI：vue-tsc / vite build
   - Go：go test / go vet
   - 真实集成：dev 运行日志

#### Exit criteria
- 已确认真实事实源
- 已确认任务边界
- 已确定最小验证路径

---

### Phase B：UI 组件 / 页面还原实施

#### 目标
按设计稿和实现方案还原 UI，而不是自由发挥。

#### 任务拆分
1. 读取并对照：
   - docs/ui-preview/index.html（最终UI交互效果）
   - docs/frontend-implementation-spec.md（前端落地实施方案）
   - 当前 frontend/src 结构
2. 按模块实现：
   - layout / sidebar / header
   - summary cards
   - table/list sections
   - actions / modal / drawer / toast
   - theme and language behavior
3. 优先级顺序：
   - 结构和样式 token
   - 状态和交互
   - 数据绑定与事件
   - 细节微调
4. 对照维度：
   - 文案
   - 间距
   - 圆角
   - 边框
   - 颜色变量
   - hover / active / focus / disabled / empty state
   - 动画与交互语义

#### 关键要求
- 不引入新依赖。
- 不改动设计稿的 DOM 语义和层级意图。
- 不做“顺手优化”式重构。
- 保持变量和样式命名与方案一致。

#### 验证
- `cd frontend && npx vue-tsc --noEmit`
- `cd frontend && npm run build`
- 逐屏对照设计稿与实际页面

#### Exit criteria
- 页面与原型一致性达到预期
- 不出现明显样式偏离
- 不出现无关重构

---

### Phase C：CLI 与 Go binding 对接

#### 目标
维护真实状态流向，确保 GUI 只做展示和聚合，而不是制造事实。

#### 任务拆分
1. 核实真实 CLI 和文件接口：
   - 命令签名
   - 参数格式
   - 文件路径
   - 端口命名
   - 环境变量/文件内容格式
2. 确认数据流：
   - CLI -> engine -> binding -> frontend 读取
   - 或 CLI -> runner -> daemon -> frontend 观察
3. 处理关键点：
   - 实际状态读取
   - 真实变更触发
   - 错误回传与日志展示
4. 保持前端只读：
   - 不给前端单独维护与真实系统同等权重的状态

#### 实施原则
- binding 层仅负责透传，不写业务逻辑。
- engine 负责解析或轻量校验。
- 真正的变更必须走 CLI 事务流。

#### 验证
- `go test ./internal/...`
- `go vet ./...`
- 若有 Wails 绑定生成，按项目约定重跑绑定生成命令
- dev 模式下观察真实输出日志，不能吞错误

#### Exit criteria
- 真实状态流经 CLI 仍然成立
- UI 不再伪造真实状态
- 关键操作返回真实日志和错误

---

### Phase D：bug 修复与根因追踪

#### 目标
修复真实缺陷，而不是掩盖症状。

#### 执行步骤
1. 复现问题：
   - 最小重现路径
   - 输入条件
   - 预期行为
   - 实际行为
2. 对比真实数据流：
   - UI state
   - api / binding
   - engine / CLI
   - 文件系统
3. 定位根因：
   - UI 层状态错误
   - binding 层参数错误
   - CLI 事实不匹配
   - 文件读取不一致
4. 做最小修复：
   - 缩小到真正导致 defect 的函数或文件
   - 不顺手重构
   - 不扩散到无关模块
5. 回归确认：
   - 检查同模块相邻行为
   - 确认没有新的回归

#### 验证
- 针对 bug 触发路径做最小验证
- UI 检查或命令验证
- Go 测试 / build 检查
- 若 bug 影响真实状态，观察实际日志和结果

#### Exit criteria
- 根因已确认并解释
- 修复行为符合真实需求
- 无同模块明显回归

---

### Phase E：任务验证与回归检查

#### 目标
在任务结束前确认“确实修好了”，而不是“看起来修好了”。

#### 执行步骤
1. 检查是否符合总纲：
   - CLI 真实事实
   - 文件接口真实状态
   - UI 还原要求
   - 最小修复要求
2. 进行最小验证集合：
   - UI：tsc / build / 对照设计稿
   - Go：go test / go vet
   - 集成：dev 运行日志
3. 检查风险：
   - 受影响模块
   - 是否存在横向回归
   - 是否有未验证的边界条件
4. 记录可交付证据：
   - 命令
   - 退出状态
   - 关键输出
   - 结论

#### 验证命令建议
- 前端：
  - `cd frontend && npx vue-tsc --noEmit`
  - `cd frontend && npm run build`
- Go：
  - `go test ./internal/...`
  - `go vet ./...`
- 若涉及运行期行为：
  - 启动 dev / 窗口并检查日志

#### Exit criteria
- 有真实验证输出
- 没有隐藏失败
- 任务结论基于证据，而不是猜测

---

## 5. 风险与注意事项

### 5.1 UI 风险
- 误改样式 token
- 改变 DOM 层级和交互语义
- 引入新依赖
- 与原型差异过大

### 5.2 CLI / binding 风险
- 伪造真实状态
- 绕过 CLI 事务流
- 依赖描述不等于真实行为

### 5.3 bug 修复风险
- 只治标不治本
- 误改无关模块
- 修复后无回归验证

### 5.4 验证风险
- 验证过浅
- 只跑编译不做真实行为检查
- 以“逻辑上正常”替代验证

---

## 6. 默认执行顺序

建议按以下顺序推进：

1. 事实核实
2. UI 对照与实现
3. Go / binding 对接
4. bug 修复与追踪
5. 验证与回归检查

不推荐跳过步骤，因为本仓库的真实约束要求：

- CLI 事实优先
- UI 设计对照优先
- 最小修复优先
- 真实验证优先

---

## 7. 交付物清单

每个任务结束前，必须准备：

- 变更概述
- 事实来源说明
- 实际影响范围
- 验证命令与输出证据
- 失败风险说明（如果有）

---

## 8. 最终判定标准

任务只有在以下条件同时满足时才算完成：

- 真实事实已核实
- 实现符合设计稿和方案要求
- CLI / 文件接口未被绕过
- 最小修复已完成
- 真实验证已执行并记录

如果缺任一项，任务不得视为完成。
